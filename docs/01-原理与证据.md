## 1. 原理

### 1.1 设备怎么把画面给出来

记录仪在自己那块 FAT32 卷的根目录放了一个特殊文件：

```
elen1  ——  固定 307200 字节
├─ 偏移 0 .. 15   : 16 字节私有头（每次读都在变，像是帧号/计数器一类）
└─ 偏移 16 起     : 一帧完整的 JPEG（SOI = FF D8，EOI = FF D9）
```

**关键机制：设备是在「文件被打开」的那一刻现做一帧的。**

所以这个文件天然就是一路**拉取式（pull）视频流**：

- **完整读一遍 = 得到一帧新的**；
- 偶尔读到的不是帧，而是一个**设备控制帧**（开头是 `55 AA ...`），跳过即可 —— 这是正常的，
  不是错误。见 §3 坑 7 与 §6。

实测的 16 字节头样例（可见每次都不同）：

```
2c 21 01 00 07 00 00 00 55 55 55 55 55 55 55 55
89 22 01 00 05 00 00 00 55 55 55 55 55 55 55 55
b3 21 01 00 08 00 00 00 aa aa aa aa aa aa aa aa
```

`0xAA` / `0x55` 是固件的填充字节（对比 `zlog` 文件：10 个 `0xAA`）。

### 1.2 官方 App 怎么做的（反编译定案）

对象：`05-逆向/APK/xapp-1101.apk` —— **XCDVR 2.3.1**，18 981 846 字节，2019-12-20，
包名 `com.williexing.android.apps.xcdvr1`。**这份 APK 是全案的转折点。**

**结论：这个 App 根本不碰 USB 传输层。** 证据：

- 用 androguard 4.1.4 全量扫 `classes.dex`（371 832 字节 / 356 个类 / 4461 条字符串），
  `claimInterface` / `bulkTransfer` / `openDevice` / `getInterface` / `getConnection` /
  `setConfiguration` / `controlTransfer` / `getDeviceList` / `hasPermission`
  —— **全部 0 处**。
- 对 `android.hardware.usb.*` 的调用**总共只有 5 处**，全在同一个方法里
  （`SystemReceiver.onReceive` 里读 `UsbDevice.getVendorId()/getProductId()`），
  **纯粹是"检测到插上了"**，然后就没有下文。
- `XUFSCameraService.openCamera` 的 JNI 签名收一个 **`jstring`**，
  原生层 `xufscam_open()` 拿它直接调 libc 的 `open()`。

真实流程：

```java
// Lcom/williexing/android/xiot/devices/g;->a(Landroid/content/Context;)Ljava/lang/String;
for (String dir : 候选挂载点) {                 // a/a/a;->c(Context) 给出的列表
    File f = new File(dir, "elen1");            // 文件名来自 g.D() 的 const-string "elen1"
    if (f.isFile() && f.length() == 307200)     // ★ 长度必须正好 307200
        if (a/a/a;->b(f)) return f.getAbsolutePath();
}
// 兜底再硬试 /mnt/usb_storage/USB_DISK0/udisk0、udisk1 ...
```

原生层 `libxufscamera.so`（22 124 字节）负责：剥 16 字节头 → `libjpeg-turbo` 解成 I420 → 交给渲染器。
它的 `.dynsym` 里**只有 JPEG 解码器**（`tjpeg2yuv*` / `jpeg_*` / `tjDecompressToYUV2` /
`packageToJavaI420Frame`），**没有任何 AVC / H.264 解码器** → 坐实预览是 **MJPEG**。

> 完整证据： [`05-逆向/APK2.3.1-逆向定案.md`](05-逆向/APK2.3.1-逆向定案.md)

### 1.3 为什么"给 App 做移植"这条思路本身是错的

**因为要移植的东西根本不存在。**

App = 一个**文件读取器 + JPEG 解码器**。真正跟 USB 打交道的是**内核**：
Android 侧能 `open()` 一个挂载卷上的文件，是因为内核已经把 U 盘挂好了。
**同一件事在 Windows 上由系统自动完成，而且早就完成了** ——
资源管理器里那个 `G:` 盘就是同一个东西。

所以：**不需要移植任何代码。** 在 Windows 上 `ReadFile` 读同一个文件，
等价于这个 App 干的全部工作。

### 1.4 它还顺便告诉我们两件事

- **U 盘挂载和 App 是并存的**（App 读的就是挂载卷）→ 说明**没有**任何一方独占 USB 设备。
- 因此反过来：**谁要是去绑 WinUSB，谁就会把 `G:` 弄没**（§7 已排除的路）。

## 3. 七个坑（全是实测踩出来的，照抄能省几小时）

1. **必须 `FILE_FLAG_NO_BUFFERING = 0x20000000`。**
   普通 `open/read` 会命中 Windows 文件缓存，连读三次拿到同一份，
   **看起来像"这个文件是静态的"**。
   ⚠️ 白天就是在这里栽的：据此写下了一条错误的"已否证 eLen1 是实时帧槽"的结论。
   加无缓冲之后：**缓存读 3 次全同；无缓冲 6 次得 5 个不同 md5**。

2. **必须读满整个 307200 字节。**
   帧 JPEG 最大能到 ~97 KB。只读前 81920 字节 → **一帧都拿不到**（截断后找不到 `FF D9`）。
   想省流量这条路是死的。

3. **每次读必须重新 `CreateFileW`。**
   句柄常开 + `SetFilePointerEx` 回绕时，读回来的是**完全不同的东西**
   （16 字节头变成 `00 00 00 00 40 4c 15 00 ...`，整段没有任何 JPEG）。
   **设备是在"打开"那一刻生成帧的。**
   好消息：`open` 只要 0.09 ms，重开几乎不花钱。

4. **读块大小必须是该卷扇区大小的整数倍**（512 或 4096）。
   这是 `NO_BUFFERING` 的硬要求。写死 512 在某些机器上会直接报 **错误 87（参数错误）**。
   → `live_view.py` 的 `detect_chunk()` 会从 65536 往下试到 512，取第一个能用的。

5. **每次读要落到缓冲区的不同偏移。**
   如果每块都读进同一个地址、最后从基址整段扫 307200 字节，
   缓冲区里**只有最后一块是真的**，其余全是 `create_string_buffer` 补的 0 → 永远找不到 JPEG。
   正确写法：`ReadFile(h, addr + got, n, ...)`。

6. **缓冲区对象必须被持有，不能被 GC 回收。**
   `ctypes.create_string_buffer(...)` 的结果如果只留了地址、对象本身没人引用，
   函数一返回就被回收，`ReadFile` 往已释放内存写 → **进程静默死亡**
   （表现为脚本只打印表头就没了，**退出码 127，没有任何报错**）。
   必须把缓冲区绑到 `self` 上，或塞进闭包的默认参数。
   *（`fps_probe.py`、`dbg_read.py` 都栽在这上面过。）*

7. **同一时刻只能有一个读取者。** ⭐ 新发现（2026-10-01 晚）
   如果同时有两个进程在读 `elen1`（比如一边开着 `--serve`、一边又跑 `--probe`），
   **两边都会拿到非 JPEG 的内容**，`--probe` 会报 "8 次读到 1 个不同帧 / (无 JPEG)"，
   帧率也会掉到 9~10。
   → **测速/自检前先停掉正在跑的服务。**
   这一条也解释了历史上 `chunk_test.py` 里出现过的异常低值（2.32 / 2.06 fps）——
   那是被并发进程污染的数据，不是真实性能。

## 4. 为什么是 20 fps 而不是 30

用户反馈"传感器的实时帧率应该是 30 fps"。实测扫描：

| 每次读多少 | 帧率 |
|---|---|
| 512 字节/块，读满 307200 | **8.7 fps**（块太小，每块固定开销拖累） |
| 4096 字节/块，读满 307200 | **20.0 fps** |
| 32768 字节/块 | 19.96 fps |
| 65536 字节/块 | 19.93 fps（再大没有收益） |
| 只读前 102400（1/3 数据） | **19.9 fps —— 没变快** |
| 只读前 81920 | **0 帧**（被截断） |

**关键判据：把读取量砍到 1/3，帧率纹丝不动。**
如果瓶颈是传输带宽，应该快 3 倍。→ **瓶颈在设备这条"拉取"通道自身**
（≈50 ms 一次的固定节拍），不在主机侧。

**但要精确说**：不能讲"读写速度完全无关"。
- 读块 512 时只有 8.7 fps → **读取实现方式仍然是变量**；
- 从 4096 往上才没有收益。
- 准确表述：**读取侧只要不拖后腿（读块 ≥ 4096），瓶颈就完全落在设备。**

**还要纠一个常见误解**：这条通路**不是标准 USB 存储协议栈**，
而是厂商固件另开的一路拉取模式。算一下就知道：
`307200 B / 50 ms ≈ 6 MB/s`，远低于 U 盘顺序读（几十上百 MB/s）。
这 50 ms 里绝大部分是**设备端在造这一帧**（曝光 + JPEG 编码 + 通过固件通道交出来）。
→ **U 盘快 ≠ 这个出口快。**

## 5. 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 找不到 `elen1` | 盘符没出现 / 设备没插好 | 看资源管理器；或 `-d X:\elen1` 手动指定 |
| 报 `err=87` | 读块不是扇区整数倍 | 换 4096 / 512，或让 `detect_chunk()` 自己探 |
| 读到 307200 字节但**没有 JPEG** | 那一次刚好是设备控制帧（不是每读必给帧） | 正常，下一轮就有；工具会自动跳过 |
| `--probe` 报 8 次全同，或全是"(无 JPEG)" | ① 有别的进程在同时读（坑 7）② 画面真的完全静止 | **先停掉其它读取者**，再重试 |
| 帧率只有 8~9 | 读块是 512 | 改成 4096 以上 |
| 进程静默退出、无报错 | 见坑 6（缓冲区被 GC） | 把缓冲区绑住 |
| 浏览器只有静态图 | 服务在跑但设备掉线 | 看页面状态行的"错误"计数 |
| 换电脑后 `--probe` 连不通 | 盘符不在 E~Z | 工具会自动扫 E~Z；实在不行 `-d` 指定 |

## 6. OSD 能不能关掉？（2026-10-01 新增）

> **一句话**：方向对（那是设备烧进画面的，只能改设备端设置），
> 但**我们从 PC 侧能走的那条文件通路是只读的**。
> 要干净画面就在主机侧裁（§6.5）。
>
> ⚠️ **2026-10-01 晚 更新 —— 本节结论降级为「未结案」**：
> 用户提供新事实：**手机 App 里似乎可以修改时间与经纬度**；
> 而我在 DEX 里**确实找到了 `settime` 这条完整代码链**
> （`TIME_SET` → 广播 → `XUFSCameraService.B()` →
> **`sendCommand2(19, 0, 0, 6 字节年月日时分秒)`**）。
> → 现在能确定的是「**主机侧这条 U 盘文件通路写不出去**」，
> **不能**再说成「这台设备不可设置」。出口在哪尚未定位。
> 全部证据 + 6 个验证实验见 [`05-逆向/待核实-时间与GPS的下行通道-2026-10-01.md`](05-逆向/待核实-时间与GPS的下行通道-2026-10-01.md)。

### 6.1 问题

抓到的帧左下角有一行信息条：

```
2017/05/01 05:28:01      E000°00'00"  N00°00'00"      0 km/h
     日期时间               经度          纬度          车速
```

用户的想法是：**这应该是可以通过信息握手在记录仪上关掉的。**

### 6.2 结论

**方向判断是对的**：那行字是设备固件**合成进 JPEG** 的（不是主机叠加的），
所以**只有"给设备端改设置"才可能去掉它** —— 主机侧再怎么处理都只是裁。

**但在当前这套「U 盘 + 官方 App」的组合里，这条"给设备改设置"的路不存在。**
不是因为找不到"开关在哪"，而是因为**整条命令通道在软件层面就是只读的**：
从 JNI 库到 Java 层，**没有任何一条代码路径能把数据写给设备**（§6.3 六条证据）。

具体卡在两处：

1. **软件侧**：官方 App 是纯读取器 —— 能读设备、能存到本地，但从不给设备写任何东西。
2. **通道侧**：即使我们想自己发厂商私有命令，也必须先绑 WinUSB 拿到那个 Bulk 端点，
   而**一绑 `G:` 就会消失** —— 等于亲手把视频通道掐死（§7）。两者互斥。

→ 所以现实的答案是：**用现有软硬件关不掉，要干净画面就在主机侧裁**（§6.5）。
→ 但**不代表这台设备在原理上不可设置** —— 见 §6.4（现在有三条没走完的路）。

> ⚠️ **注意本节的适用边界**：上面证明的是「**主机侧这条 U 盘文件通路**读得到、写不出去」，
> **不能**推广成「这台设备整体不可设置」。真要动设备设置，得先找到**下行通道** ——
> 那正是 [`05-逆向/待核实-时间与GPS的下行通道-2026-10-01.md`](05-逆向/待核实-时间与GPS的下行通道-2026-10-01.md) 要解决的事。

### 6.3 证据链（六条，互相独立）

**① `libxufscamera.so` 没有任何"写出去"的能力。**
```
03-工具 → 05-逆向/脚本/osd_probe.py   （可复跑，30 秒）

.dynsym 共 134 项：导入 58 项。
其中与 I/O 有关的只有：
    open / close / read / lseek / fstat / fopen / fclose / fprintf / sprintf / memcmp / memcpy
★ write / pwrite / send / sendto / ioctl / libusb —— 一项都没有。
```
→ **这个库在物理上无法向设备写一个字节。** 它能做的全部 I/O = 打开一个文件、读它、关掉。

**② `sendCommand2` 这条链是死代码。**
`xufscam_send_command2` @0x32c5 有 132 字节实体（不是空桩），反汇编显示它
`malloc(80)` → 填一条 80 字节记录 → `Enqueue` 进内存队列。
**但这个库里没有任何 write/ioctl 能把队列送出去。** → 命令进了队列就没了。

> 旁证：2018 年随机附带的那版 `libnative-lib.so` 里，
> `setFileDescriptor` / `getFileDescriptor`（把 usbfs 的裸 fd 交给原生层做双工）是**真实实现**；
> 而在 2.3.1 这版 `libxufscamera.so` 里，这两个符号是 **4 字节空桩**（`movs r0,#0; bx lr`）。
> → **厂商在改成"读 U 盘文件"这个方案时，把双工能力删掉了，只留只读。**
> 那 19 个 `sendCommand2` 调用全部是**改版时没删干净的残留**。

**③ App 里没有任何 OSD/水印设置项。**
把 2.3.1 的 `classes.dex` 字符串表**全量导出**（4461 条）后：
- 含中文的 **139 条**，逐条看过：全部是**电子狗 / ADAS 预警 / GPS 测速校准 / 授权**
  相关（"固定测速照相""车道偏离 请注意""GPS速度微调""调整摄像头角度，车身请勿超过红线"…）。
  **没有一条**是关于时间水印、画面叠加、OSD 开关的。
- 全局搜 `osd|water|stamp|logo|overlay` 的命中只有：
  `MANAGE_OVERLAY_PERMISSION`、`canDrawOverlays`、`no_draw_overlay_permission`、
  `ic_branding_watermark_white_48dp`、`menu_ic_branding_watermark_white`、`timestamp`。
  → 前五个全是 **Android 自己的悬浮窗权限 + App 图标资源**（对应 App 里那个
  "桌面浮标是否显示"的悬浮车速球），`timestamp` 是通用串。
  **与设备端 OSD 无关。**

**④ 19 个已知命令号里没有 OSD 类。**
从 `dex_sendcommand2_sites.txt` 汇总出的全部命令号：
`0, 1, 2, 3, 4, 5, 12, 13, 14, 17, 19, 20, 21, 22, 29, 32, 33, 34, 39`
已知语义的几个：`1` = 开始录像、`5` = 预览、`12/13/14` = 设置时间、
`32` = 上传 GPS 数据、`33` = GPS 上报开关、`29`（带 arg 3000，疑似心跳/间隔）。
**没有任何一个看起来像"显示开关"。**

**⑤ 卷上根本没有配置文件。**
`G:` 根目录只有三个文件：`elen1`（307200，只读+存档）、`uCarDvr.apk`（494798）、
`zlog`（10 字节全 `0xAA`）。加上 Windows 挂载时自己建的两个
`System Volume Information\*`。**没有任何 `.ini` / `.cfg` / `.txt` 可供改设置。**

**⑥ ⭐ Java 层也没有任何一处「往设备写」的代码。**（2026-10-01 补测）
上一轮只看 JNI 库，有人会合理质疑：Java 层不需要经过那个 `.so` 也能写文件
（`FileOutputStream` 是纯 Java 的）。
→ 于是把 2.3.1 的 `classes.dex` **全量扫了一遍所有"写"相关调用**
（`FileOutputStream` / `RandomAccessFile` / `FileWriter` / `getOutputStream` /
`createNewFile` / `setWritable` / `renameTo` / `mkdirs` …），脚本
`05-逆向/脚本/apk231_writes.py`，输出 `05-逆向/原始输出/apk231_writes.txt`。

**命中 16 个方法，逐个看过，没有一个是往设备/U 盘写的。** 全部落在这几类：

| 用途 | 例子 |
|---|---|
| **把设备过来的画面存到手机本地** | `Lcom/williexing/.../XUFSCameraService$b;->run()` |
| 电子狗数据 / 崩溃日志 / 授权文件 | `CrashHandler`、`ToolUtils.copyBaseFile`、`LicenseInterface` |
| ADAS 执行外部命令（`/system/bin/su`） | `Lcom/sinosmart/adas/CommandUtil` |
| 解压资源到 App 私有目录 | `La/a/a/b/a/a/a/*` |

其中唯一跟摄像头有关的那个，全文只有这一件事：

```java
// Lcom/williexing/android/xiot/devices/XUFSCameraService$b;->run()V
YuvImage yuv = a(frame, 17);
FileOutputStream fos = new FileOutputStream(path);        // path 由调用方传入
yuv.compressToJpeg(new Rect(0, 0, w, h), 86, fos);        // ← 把当前帧存成一张 JPEG
fos.flush(); fos.close();
```

而 `path` 的来源（`La/a/a/a/a/a/c;->a(Intent, String)`）：

```java
new File("/sdcard/XCDVR").mkdirs();
new File("/sdcard/XCDVR/Videos").mkdirs();
new File("/sdcard/XCDVR/Images").mkdirs();
// 命令 "takepicture2" → PIC-<yyyyMMdd-HHmmss-SSS>.jpg  放进 /sdcard/XCDVR/Images
// 命令 "startrecord2" → VID-<yyyyMMdd-HHmmss-SSS>.mp4  放进 /sdcard/XCDVR/Videos
```

**全是手机自己的 `/sdcard`。** 也就是说 ——
**这个 App 对外的"写"只有一件事：把设备给的画面存到手机里。它从不给设备写任何东西。**

> 一句话总结这一节：**App 能"读设备"，能"存到本地"，但没有任何一条代码路径能"告诉设备任何事"。**
> 想改设备端的 OSD，需要的正是最后那件事。

### 6.4 还没排除的可能（三条：两条可测、一条不建议试）

先说清楚**这一节的结论边界**：
上面证明的是「**在主机侧这条 U 盘文件通路上，没能把任何参数送到设备**」，
**不是**「这台设备在原理上不可能被设置」。OSD 是设备固件合成的，
**要关它，只可能靠"给设备端改设置"** —— 这个方向判断本身是完全正确的。

问题是这条路在哪。

---

**(a) 手机上的 App 可能是更新的版本** —— 可测，1 分钟

上面验的是 **XCDVR 2.3.1（2019-12）**。**他手机上装的可能是更新的版本。**

这里有个逻辑闭环：新版 App 如果**也**能一边出画面、一边让 U 盘挂载着，
那它仍然只能是文件读取器，**照样没有命令通道**。
只有当新版 App **抢占了 USB 设备**（把 U 盘踢掉）时，才说明它拿到了真正的控制通道。

> **在手机上 1 分钟验证：**
> 打开手机 App，进到能看到实时画面那一页。
> 这时切到手机自带的**文件管理器**，看还能不能看到那个 U 盘（能不能看到 `elen1` 文件）。
>
> - **能看到** → App 是纯文件读取 → **没有命令通道** → 与本结论一致
> - **看不到 / 提示 U 盘已移除** → App 抢占了 USB → **命令通道存在** → 这条路才有讨论价值

---

**(b) 设备可能在开机时读 U 盘上的某个配置文件** —— 理论可行，**但没有证据，且不建议乱试**

很多行车记录仪确实是"往卡里放一个 `config.txt` / `.ini` 就改设置"。
这条路的诱人之处是：**不需要 USB 私有协议，所以就绕开了"绑 WinUSB 会让 `G:` 消失"这个死结。**

但是：

- **零证据。** 设备插了这么久、卷被完整枚举过多次，
  **从来没有出现过任何配置文件**（只有 `elen1` / `uCarDvr.apk` / `zlog`）。
  固件里的格式串也只有 `MOVI%04d.avi` / `LOCK%04d.avi` / `PICT%04d.jpg` —— **没有配置文件的影子**。
- **只能靠猜。** 文件名、格式、放在根目录还是子目录，全都不知道。
  猜错时最可能的结果是"被忽略"，但**不排除固件解析到畸形内容后行为异常**。
- 另外，`elen1` 带**只读属性**，而设备自己每次读都在重写它 ——
  说明这个卷不是按标准 FAT32 语义来管理的，**在它上面乱写东西不是零风险**。

→ **结论：在没有厂商文档或同型机资料之前，我不建议拿它做实验。**
如果哪天真的想试，最低风险的做法是：单独一张空 TF 卡 / 空 U 盘，
只放一个候选配置文件，插上后看 U 盘根目录会不会多出东西、画面会不会变 ——
**不要动带 `elen1` 的那块卷。**

---

**(c) ⭐ 下行通道可能根本不是"U 盘文件"这条路** —— 2026-10-01 晚新增

用户观察到：**App 里可以修改时间戳与经纬度**。而 DEX 里确实存在完整链条：
`TIME_SET` → 广播 → `XUFSCameraService.B()` →
**`sendCommand2(19, 0, 0, 6 字节年月日时分秒)`**。
→ 说明**"改设备设置"这个意图在 App 代码里是真实存在的**，只是**出口还没定位**。

三种可能（**都未验证**）：

1. 改的其实是 **App 自己的显示/状态**（它有 `SYSTEM_ALERT_WINDOW` 悬浮窗权限）；
2. 手机上的 App 是**比 2.3.1 更新的版本**（2018 版有双工、2.3.1 版被删成 4 字节空桩，
   说明厂商有能力删、也有能力加回来）；
3. 下行**不走这个 `.so`**，而是往卷里写文件（卷是 FAT32、**可写**、空着 1 GB、无只读标记），
   或者走网络（App 有 `INTERNET` 权限，且存在 `command / getstatus / connect` 这组"像 HTTP"的串）。

**验证方法与全部新证据见**
[`05-逆向/待核实-时间与GPS的下行通道-2026-10-01.md`](05-逆向/待核实-时间与GPS的下行通道-2026-10-01.md)。
其中最便宜的一个：**在 App 里改一次时间，然后看画面左下角那行水印变不变** ——
10 分钟就能排掉第 1 种可能。

### 6.5 绕开办法：软件裁掉（**一条命令**）

既然关不掉，就**在主机侧裁掉**——反正我们本来就要把帧转出去。

```cmd
cd tools

:: ★ 一条命令：边看边裁（服务端裁好再发，浏览器拿到的就是干净画面）
python live_view.py --serve --crop 80

:: 存帧时一起裁
python live_view.py --save -n 60 --crop 80
```

`--crop N` = 裁掉画面底部 N 像素。实测 OSD 文字带正好在 **y = 674..719**，
所以 **`--crop 80` 足够**（多留了一点余量，怕不同固件版本行高不同）。
`--crop-quality` 默认 85（`keep` 反而更大：源 72 KB → keep 112 KB / q70 60 KB / q85 84 KB / q95 131 KB）。

> ⚠️ **`--crop` 需要 Pillow**（`pip install pillow`）——**只有加 `--crop` 才需要**，
> 不加时 `live_view.py` 仍然是零依赖的纯标准库程序。

**另外两个工具，看你要哪种：**

| 场景 | 命令 |
|---|---|
| 裁已有的图片文件（批量 / 原地） | `python crop_osd.py --in-place 图.jpg` |
| 先量一下该裁多少（真的去数像素） | `python crop_osd.py --probe 图.jpg` |
| 起一个独立的"已裁"实时流（不动 `live_view`） | `python crop_osd.py --proxy` → `http://127.0.0.1:8082` |
| 连 Python 都不想用 | `ffmpeg -i http://127.0.0.1:8081/stream -vf "crop=1280:640:0:0" out.avi` |

实测：`--serve --crop 80` 稳定 **20.2 fps / 0 错误**，输出 **1280×640**。
（单帧体积会略涨到 ~110 KB，因为 Pillow 的重编码不如设备硬件编码器紧凑；
嫌大可加 `--crop-quality 70`。）

**但我的建议仍然是：先别裁。** 理由：

- 这行 OSD 里的**时间戳是免费的掉线判据** —— 画面看着"没动"时，
  看时间戳有没有在走，比算 md5 直观得多；
- 而且它是**烧进 JPEG**的（不是叠加层），所以它一定反映设备端真实状态。
- 目前 GPS 是 `E000°00'00" N00°00'00"`（未定位）、车速 `0 km/h`、日期 `2017/05/01`
  （固件默认 RTC）—— 也就是说这行**只有时间戳在动**。
  真要给别人看录像时再裁。

## 9. 还没做的（可选，留个方向）

1. **查 OSD 的路还剩三条**：见 §6.4，其中「在 App 里改一次时间、看画面水印变不变」只要 10 分钟。
2. **突破 20 fps / 改分辨率**：得找设备的控制口。走 U 盘这条通道没找到；
   那需要发厂商私有 USB 命令（协议格式 `55 AA` + 小端 5 字段 +
   `cks = (0xAA55 + cmd + arg + len) & 0xFFFF` 曾经被完整还原过），
   **但要绑 WinUSB，而绑了 `G:` 就没——两条路互斥。**
3. **掉线判据**：用 OSD 里的时间戳做"画面是否卡死"的检测（比 md5 直观）。
4. **接别的消费程序**：直接拉 `http://127.0.0.1:8081/stream`（标准 MJPEG），
   OpenCV / ffmpeg / 各种网页播放器都认。
