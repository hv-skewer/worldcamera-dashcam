# 02 · 部署到另一台电脑

> 全部数字都是在本机实测出来的（2026-10-01）。**本方案不需要装驱动、不需要 Zadig、
> 不需要管理员权限、不碰任何系统设置。零第三方依赖。**
>
> 技术原理与完整证据见 [`01-原理与证据.md`](01-原理与证据.md)。

---

## 一句话原理

这块记录仪（`WORLDCAMERA-MSDC`）把它 U 盘根目录下一个叫 **`elen1`** 的文件
当成"当前画面"的出口：

```
elen1（固定 307200 字节）
├─ 偏移 0 .. 15   : 16 字节私有头（每次读都在变）
└─ 偏移 16 起     : 一帧完整的 JPEG（1280×720，约 50–97 KB）
```

**每完成一次「打开 → 读满 → 关闭」，设备就现做一帧。** 所以它天然是一路视频流。

官方安卓 App 也是这么干的 —— 它**根本不碰 USB 传输层**，只是在挂载卷上找
`size == 307200` 的 `elen1`，然后 `open()` + `read()`。

**唯一的坑：Windows 文件缓存。** 普通 `open/read` 会命中缓存，连读三次拿到同一份，
看起来像"文件是静态的"。必须用 `FILE_FLAG_NO_BUFFERING` 直读。

## 三步部署

### 1. 确认设备在位

```cmd
cd tools
python live_view.py --probe
```

期望输出：找到 `X:\elen1`，**连读 8 次得到 8 个不同的 md5**。

```
设备文件 : G:\elen1
槽位大小 : 307200 字节（固件固定值）

[自检] 连续读 8 次，看是否是不同帧……
  #0  06b9a3c5e7fb  94752 字节
  #1  f987f6d43cf0  94618 字节
  ...
  8 次读到 8 个不同帧，耗时 0.43s（18.7 次/秒）
  ✅ 帧在变化 —— 通道通了。
```

**盘符自动探测**（E~Z 都扫，跳过 C 系统盘和 D 光驱），不用改代码。认不出来就手动指定：

```cmd
python live_view.py -d H:\elen1 --probe
```

### 2. 看实时画面

```cmd
python live_view.py --serve
::  然后浏览器打开  http://127.0.0.1:8081
```

页面会显示实时画面 + 一行状态（帧大小 / fps / 累计帧数 / 错误数）。

想去掉画面左下角那行 OSD（时间/经纬度/车速），加一个参数就行（需 Pillow）：

```cmd
python live_view.py --serve --crop 80
```

| 端点 | 用途 |
|---|---|
| `/` | 带状态栏的观看页 |
| `/stream` | MJPEG 流本身（标准 `multipart/x-mixed-replace`，可嵌页面 / 给别的程序拉） |
| `/snapshot` | 单张 JPEG 快照（适合定时截图、做告警） |
| `/stat` | JSON 状态：`{"seq","fps","reads","errors","frame_kb"}` |

换端口：`python live_view.py --serve -p 9000`
允许局域网访问：`--host 0.0.0.0`（⚠️ 无鉴权，只在可信网络里开）

### 3. 只想存帧 / 只测速

```cmd
python live_view.py --save -n 300          :: 存 300 帧到 frames/
python live_view.py --fps                  :: 只测帧率（10 秒）
python live_view.py --save -n 60 --interval 1.0   :: 每秒一张，存 60 张
```

## 实测性能（本机数据，供对照）

| 指标 | 数值 |
|---|---|
| 分辨率 / 编码 | 1280×720 / **MJPEG（JPEG）** |
| 单帧大小 | 约 50–97 KB（随画面复杂度变） |
| **稳定帧率** | **20.0 fps**（200 帧 / 10 秒，0 错误） |
| 有效码率 | ≈ 6 MB/s |
| 单帧耗时 | open **0.09 ms** + read **46.9 ms** + close **0.02 ms** |
| 读块 / 每帧读次数 | 65536 / 5 次（工具自动探测） |
| CPU 占用 | 很低（只是读文件 + HTTP 转发） |

### 关于"能不能到 30 fps"

**到不了，而且不是我们读得慢。** 实测证据：

| 每次读多少 | 结果 |
|---|---|
| 512 字节/块，读满 307200 | 8.7 fps（每块固定开销拖慢） |
| 4096+ 字节/块，读满 307200 | **20.0 fps** |
| 只读前 102400（1/3 数据） | 19.9 fps —— **没变快** |
| 只读前 81920 | **0 帧**（帧被截断，找不到 EOI） |

**关键判据：把读取量砍到 1/3，帧率纹丝不动。** 如果瓶颈是带宽，应该快 3 倍。
→ 瓶颈在**设备这条"拉取"通道自身**（约 50 ms 一次的固定节拍）。

补一句：也不能说"读写速度完全无关" —— 读块 512 时只有 8.7 fps，
所以**读取实现方式仍是变量**；从 4096 往上才没有收益。
准确表述是：**读取侧只要不拖后腿，瓶颈就完全落在设备。**

⚠️ 还要纠一个直觉错误：**"U 盘支持高速读写" ≠ "这个出口快"。**
这条通路不是标准 USB 存储协议栈，是厂商固件另开的一路拉取模式：
`307200 B / 50 ms ≈ 6 MB/s`，远低于 U 盘顺序读。这 50 ms 里绝大部分是
**设备端在造这一帧**（曝光 + JPEG 编码 + 交出来）。

**推荐读块：65536**（工具会自动探测，探测失败退到 4096 / 512）。

## ⚠️ 七个坑（全是我实测踩出来的，照抄会省很多时间）

1. **必须绕过文件缓存。**
   用 `CreateFileW(..., FILE_FLAG_NO_BUFFERING, ...)`。
   否则连读三次全是同一份缓存，会误判成"文件是静态的" —— 我在这上面栽过一次，
   写下过一条错误的"已否证"结论。

2. **必须读满整个 307200 字节。**
   帧 JPEG 最大能到 ~97 KB。只读前 81920 字节会**一帧都拿不到**（截断后没有 `FF D9`）。
   想省流量这条路是死的。

3. **每次读必须重新 `CreateFileW`。**
   实测：句柄常开 + `SetFilePointerEx` 回绕时，读回来的是**完全不同的东西**
   （16 字节头变成 `00 00 00 00 40 4c 15 00 ...`，整段没有任何 JPEG）。
   **设备是在"打开"那一刻生成新帧的。**
   好消息：open 只要 0.09 ms，重开几乎不花钱。

4. **读块大小必须是该卷扇区大小的整数倍。**
   `NO_BUFFERING` 的硬要求。多数是 512，但也可能是 4096。
   写死 512 在某些机器上会直接报 **错误 87（参数错误）**。
   → 工具里 `detect_chunk()` 会从 65536 往下试到 512，取第一个能用的。

5. **每次读要落到缓冲区的不同偏移。**
   如果每块都读进同一个地址、最后从基址整段扫 307200 字节，
   缓冲区里**只有最后一块是真的**，其余全是 0 —— 于是永远找不到 JPEG。
   正确做法：`ReadFile(h, addr + got, n, ...)`。

6. **缓冲区对象必须被持有，不能被 GC 回收。**
   `ctypes.create_string_buffer(...)` 的结果如果只留了地址、对象本身没人引用，
   函数一返回它就被回收，`ReadFile` 往已释放内存写 → **进程静默死亡**
   （表现为脚本只打印表头就没了，**退出码 127，没有任何报错**）。
   必须把缓冲区绑到 `self` 上或塞进闭包的默认参数。

7. **同一时刻只能有一个读取者。** ⭐
   如果同时有两个进程在读 `elen1`（比如一边开着 `--serve`、一边又跑 `--probe`），
   **两边都会拿到非 JPEG 的内容**：`--probe` 会报"8 次读到 1 个不同帧 /(无 JPEG)"，
   帧率掉到 9~10。
   → **测速、自检之前先停掉正在跑的服务。**
   （历史上 `chunk_test.py` 里出现过的 2.32 / 2.06 fps 就是这个原因，不是真实性能。）

## 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 找不到 `elen1` | 盘符没出现 / 设备没插好 | 看资源管理器；或 `-d X:\elen1` 手动指定 |
| 报 `err=87` | 读块不是扇区整数倍 | 换 4096 / 512；或让 `detect_chunk()` 自己探 |
| 读到 307200 字节但**没有 JPEG** | 那一次刚好是设备控制帧（不是每读必给帧） | 正常，下一轮就有；工具会自动跳过 |
| `--probe` 报 8 次全同 / 全是"(无 JPEG)" | **坑 7**：有别的进程在同时读 | 先停掉其它读取者，再重试 |
| 帧率只有 8~9 | 读块是 512 | 改成 4096 以上 |
| 进程静默退出、无报错 | 见坑 6（缓冲区被 GC） | 把缓冲区绑住 |
| 浏览器只有静态图 | 服务在跑但设备掉线 | 看页面状态行的"错误"计数 |
| 换电脑后连不通 | 盘符不在 E~Z | 工具自动扫 E~Z；不行就 `-d` 指定 |
| 画面里的时间戳不走了 | **真掉线**（OSD 是设备烧进 JPEG 的，它不动就是设备不动） | 检查 USB 连接 |

## 画面左下角那行 OSD（时间 / 经纬度 / 车速）

**先说结论（精确版）：**

- **方向判断是对的** —— 那行字是**设备固件合成进 JPEG** 的（不是主机叠加的），
  所以**只有"给设备端改设置"才可能去掉它**，主机侧再怎么处理都只是裁。
- **但当前这套「U 盘 + 官方 App」的组合里，"给设备改设置"这条路不存在。**
  不是"开关藏在哪"没找到，而是**整条命令通道在软件层面就是只读的**：
  从 JNI 库到 Java 层，**没有任何一条代码路径能把数据写给设备**。
- **这不代表这台设备在原理上不可设置。** 三条还没走完的路见
  [`01-原理与证据.md`](01-原理与证据.md) §6.4。
- ⚠️ **2026-10-01 晚 更新**：用户说 **App 里能改时间与经纬度**，而 DEX 里**确实有**
  `settime` 这条链（`TIME_SET` → 广播 → `XUFSCameraService.B()` → `sendCommand2(19, …)`）。
  → 本节结论**降级为"未结案"**：能确定的是"**主机侧这条文件通路写不出去**"。
  出口在哪、怎么验，见
  [`05-逆向/待核实-时间与GPS的下行通道-2026-10-01.md`](05-逆向/待核实-时间与GPS的下行通道-2026-10-01.md)。

完整证据共 **6 条，互相独立**，见 [`01-原理与证据.md`](01-原理与证据.md) §6.3。摘要：

| # | 证据 | 结论 |
|---|---|---|
| ① | `libxufscamera.so` 的 58 个导入符号里没有 `write`/`send`/`ioctl`/`usb_` | 这个库物理上无法向设备写一个字节 |
| ② | `sendCommand2` 链进了内存队列就没有出口；2018 版的 `setFileDescriptor` 在 2.3.1 里成了 **4 字节空桩** | 厂商主动删掉了双工能力，只留只读 |
| ③ | DEX 字符串表 4461 条全量导出，139 条中文逐条看过 | 没有一条跟 OSD/水印开关有关 |
| ④ | 19 个已知命令号 `0,1,2,3,4,5,12,13,14,17,19,20,21,22,29,32,33,34,39` | 没有一个像"显示开关" |
| ⑤ | `G:` 根目录只有 `elen1` / `uCarDvr.apk` / `zlog` | 卷上没有任何配置文件 |
| ⑥ | ⭐ 全量扫 `classes.dex` 所有"写"相关调用（16 个方法） | **没有任何一处是往设备写**；唯一的摄像头写操作是把帧存到手机自己的 `/sdcard/XCDVR/Images` |

> 一句话：**App 能"读设备"，能"存到本地"，但没有任何一条代码路径能"告诉设备任何事"。**

**想干净画面就在主机侧裁掉** —— 一条命令：

```cmd
cd tools

:: ★ 边看边裁：服务端裁好再发，浏览器拿到的就是干净画面
python live_view.py --serve --crop 80

:: 存帧时一起裁
python live_view.py --save -n 60 --crop 80
```

`--crop N` = 裁掉底部 N 像素。实测 OSD 文字带在 **y = 674..719**，
所以 `--crop 80` 足够（留了点余量）。实测 **20.2 fps / 0 错误**，输出 **1280×640**。
嫌体积大可以加 `--crop-quality 70`（默认 85；`keep` 反而更大）。

> ⚠️ **`--crop` 需要 Pillow**（`pip install pillow`）——
> **只有加 `--crop` 才需要**，不加时 `live_view.py` 仍是零依赖的纯标准库程序。

**另外几个工具，看你要哪种：**

```cmd
:: 先量一下该裁多少（它真的去数像素，不改文件）
python crop_osd.py --probe ..\06-样本\帧\frame_000.jpg
::  → 检测到 OSD 带：y = 674 .. 719  → 建议 --height 54

:: 裁单张 / 批量 / 原地覆盖
python crop_osd.py 图.jpg
python crop_osd.py --in-place ..\06-样本\帧\*.jpg
python crop_osd.py --height 80 --quality 80 图.jpg

:: 或者起一个独立的"已裁"实时流代理（不动 live_view）
::   终端 A
python live_view.py --serve                      :: 原始流 :8081
::   终端 B
python crop_osd.py --proxy                       :: 裁好的流 :8082
::   浏览器开 http://127.0.0.1:8082
```

实测：裁切代理转发 **19.8 fps / 0 错误**，输出 1280×640。

**但我的建议是先别裁**：OSD 里的时间戳是**免费的掉线判据**
（画面看着没动时，看时间戳走不走比算 md5 直观得多）。
目前那行只有时间戳在动（GPS 未定位、车速 0、日期是固件默认的 2017/05/01），
真要给别人看录像时再裁。

## 试过了、走不通的路（别再花时间）

| 方案 | 为什么不行 |
|---|---|
| 绑 WinUSB（Zadig）+ libusb 读 Bulk 端点 | **不但没用，而且有害**：绑了之后 `G:` 会消失，把唯一能走的路堵死 |
| 从 Bulk 端点走厂商私有协议取视频 | 那两个 Bulk 端点是大容量存储（SCSI Bulk-Only），视频走的是**文件** |
| 找第二块盘 / TF 卡里的视频 | 可移动卷只有 `G:` 一个；TF 卡录像（AVI/AV1）是**另一条通路**，与实时预览无关 |
| 给这个安卓 App 做移植 | **伪命题** —— App 只是个文件读取器，真正跟 USB 打交道的是内核 |
| 改画面分辨率 / 帧率 | 需要厂商私有控制通道 → 要绑 WinUSB → 与 U 盘通路互斥 |
